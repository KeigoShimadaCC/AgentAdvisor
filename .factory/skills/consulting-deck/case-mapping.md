# Mapping an AgentAdvisor case to a deck

Read this only when the deck summarises a case under `cases/<case-id>/`. The
deck is a *view* of validated artifacts, so it must be generated by reading
those files, never by retyping numbers a model reported in conversation.

## Where the inputs live

| Artifact | Path (relative to the case root) |
| --- | --- |
| Decision spec | `shared/decision_spec.yaml` |
| Intake record | `shared/intake_record.yaml` |
| Issue tree | `shared/issue_tree.yaml` |
| Evidence records | `shared/evidence/E-*.yaml` |
| Evidence critique | `shared/evidence_critique.yaml` |
| Assumptions | `shared/assumptions/A-*.yaml` |
| Objections | `shared/objections/O-*.yaml` |
| Pre-mortem | `shared/premortem_report.yaml` |
| Preliminary recommendation | `shared/preliminary_recommendation.yaml` |
| **Final recommendation** | `outputs/final_recommendation.yaml` |
| Quantitative results | `analysis/T-*/results.yaml` |
| Rendered markdown | `outputs/final_recommendation.md` |
| Track divergence | `shared/track_divergence.yaml` |
| Disclosure record | `shared/disclosure_record.yaml` |

Load YAML with `yaml.safe_load`. If `outputs/final_recommendation.yaml` is
missing, the case has not reached synthesis and there is no deck to build; say
so rather than assembling one from partial artifacts. Note the final
recommendation is the one artifact written under `outputs/`, not `shared/`;
everything else in this table is under `shared/`.

## Slide plan

`FinalRecommendation` maps onto the standard arc almost field for field.

| Slide | Source fields |
| --- | --- |
| Title | `decision_spec.yaml` question, case id, run date |
| Executive summary | `recommended_action`, `timing`, `decision_confidence_summary`, top 3 `key_reasons` |
| The decision | decision spec objectives and constraints |
| What was assessed | `alternatives_considered` count, evidence count, objection count, `analysis/` task count |
| Why (one slide per reason) | `key_reasons`, each paired with its `citations` and any `quantitative_findings` |
| Alternatives | `alternatives_considered` as a `.tbl` sorted by `rank`, recommended row `class="hl"` |
| Scenarios | `scenario_analysis` — `scenario_bars()` over each `probability.point`, `summary` in the rail |
| Uncertainty | `outcome_probabilities`, `evidence_confidence`, `recommendation_confidence`, `model_stability` |
| Challenge | `strongest_counterarguments`, plus unresolved entries from `shared/objections/` |
| Assumptions | `critical_assumptions`, with the assumption ledger's status as a `.tag` |
| What would change this | `recommendation_change_triggers` |
| Next actions | `next_actions` as a `.tbl` with owner and date columns |
| Appendix: evidence | `shared/evidence/E-*.yaml` — id, claim, source, date, `independence_group` |
| Appendix: method | stages run, model per role, budget consumed from the audit log |

## The uncertainty slide

This slide is where a decision deck usually goes wrong, and this repository has
a hard architectural rule about it: **outcome probability, evidence confidence,
recommendation confidence and model stability are four different quantities and
must never be merged into one number, one gauge, or one traffic light.**

Give each its own `.kpi` in a four-up `.kpis` band, with the basis text beneath:

```html
<div class="kpis">
  <div class="kpi">
    <span class="kpi__val">62%</span>
    <span class="kpi__lab">Base case probability</span>
  </div>
  <div class="kpi">
    <span class="kpi__val">0.55</span>
    <span class="kpi__lab">Evidence confidence</span>
  </div>
  <div class="kpi">
    <span class="kpi__val">0.70</span>
    <span class="kpi__lab">Recommendation confidence</span>
  </div>
  <div class="kpi">
    <span class="kpi__val">7/9</span>
    <span class="kpi__lab">Sensitivity runs supporting</span>
  </div>
</div>
```

Then print each measure's `basis` string in the body. A confidence value without
its basis is not reportable. `model_stability` is a count of sensitivity runs,
not a probability, so render it as `runs_supporting/runs_total` and never as a
percentage that could be read as likelihood.

For `probability.point`, show `interval_low`–`interval_high` alongside it
whenever those fields are populated, and name the `method` and
`reference_class` in the source line. A bare point estimate misrepresents the
work behind it.

## Citations

`FinalRecommendation.citations` and the inline `[E-NNN]` / `[A-NNN]` markers in
the recommendation text are the audit chain. Keep the markers in the slide text
and resolve them in the evidence appendix, so a reader can go from a claim on
slide 5 to the source record. Do not silently drop a marker because it clutters
a bullet; shorten the bullet instead.

Evidence records carry `independence_group`. If several citations behind one
reason share a group, they are one source, and the slide should say so rather
than implying independent corroboration.

## Scope note

Generating this deck from a script under `tmp/` is tooling. Wiring deck
generation into the orchestrator as a pipeline stage or a CLI subcommand is
product functionality, which under `AGENTS.md` needs an approved spec in
`specs/` and a ROADMAP entry first. Do not add it to `orchestrator/` without
one. That wiring shipped in `specs/phase-8-pipeline-improvement/SPEC-057-deck-deliverable.md`
(status `verified`): the orchestrator now generates a deck automatically at `done` and via
`advisor deck <case-id>`. This skill remains the by-hand path for ad-hoc or exploratory decks.
