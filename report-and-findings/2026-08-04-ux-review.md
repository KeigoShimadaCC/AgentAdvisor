# UX review of the web surface — eight areas, ordered by impact

**Date:** 2026-08-04
**Scope:** `frontend/` and the service edges in `orchestrator/service/`. Reviewed against commit
`8bb0425`.
**Constraint:** the backend pipeline flow stays as it is. Across all twelve recommendations below
the total backend surface is two additive audit events, two lexicon rows, one control function
switched to the background worker it already has, and one optional field on a list endpoint. No
stage, transition, handler, or artifact schema changes.

The engine already produces the hard thing: an auditable chain from question to recommendation with
four kinds of uncertainty kept separate. The web surface loses most of that on the way to the
screen.

## Keep these

They are better than the norm at this stage and the work below should preserve them:

- **The copy discipline.** `frontend/src/copy/terms.ts` and
  `orchestrator/service/lexicon_data.yaml` mean no raw `CaseStage`, `TaskRole` or artifact field
  name reaches the DOM.
- **Honest empties.** `EMPTY_TRUTHS` distinguishes "Not yet" from "Nothing found" from "Cut at
  limit". Almost nobody makes that distinction.
- **The audit log as the nervous system.** One append-only chronology, line-cursor addressable,
  replayable. The right foundation — it is simply underused.
- **Four uncertainty encodings that never collapse into one number**, plus an explicit
  `NotAssessed` sentinel. This is the product's identity and should become its visual identity.

## 01 — The first five minutes are a blank screen

**Severity: trust-critical.**

You type a decision, press *Frame this decision*, and the button becomes the word "Framing…" for
minutes. No case exists as far as the UI is concerned; you cannot cancel; a reload loses the prompt
with no way to tell whether a case was created.

- `orchestrator/service/app.py:481` — `POST /api/cases` calls `new_case()` synchronously, which runs
  the worker through intake *and* framing before returning a `case_id`.
- `frontend/src/screens/NewDecision/NewDecision.tsx:38` — the client awaits that call.
- `orchestrator/service/app.py:513` — the fix pattern is already in the file: `approve_framing`
  passes `worker_runner=spawn_worker_background`. Only `new_case` blocks.

**What to do**

- Return the case immediately: create the directory, audit `control_case_created`, respond `202`
  with the id, run intake+framing on the background worker. The client routes to the case shell in
  ~200 ms and streams from there.
- Make the wait the first demonstration of the method. Intake and framing are the most explicable
  part of the pipeline; narrating them is a 90-second onboarding to how the system thinks, on time
  currently spent on a disabled button.
- Draft-persist the prompt to `localStorage` on every keystroke.

*Backend: one control-layer change, mirroring the approve path. No pipeline flow change.*

## 02 — The stream goes quiet exactly when the wait is longest

**Severity: trust-critical.**

The SSE stream works; the problem is what it carries. The audit log records an invocation *after it
returns*, so during the single longest wait in the product — a multi-minute agent call — the stream
emits nothing.

This produces an inversion in `LiveActivity`: it infers "running" from the last attempt whose status
is *not* `ok`. A healthy long-running agent therefore renders as the *previous* agent, greyed out,
marked "completed". The UI is most reassuring when something is going wrong and silent when
everything is fine.

- `orchestrator/invoke_role.py:224` — `role_invocation_attempt` is emitted post-hoc with
  `duration_ms` and usage. There is no "started" event.
- `frontend/src/screens/Brief/LiveActivity.tsx:120` —
  `isRunning = attemptActive && status !== "completed"`.
- `frontend/src/screens/shared/useCaseView.ts:25` — the projection is fetched **once per mount** and
  never again. `brief_sections`, `rooms` and `uncertainty` are frozen at page load. The living brief
  is not living.
- `frontend/src/api/sse.ts:69` — no reconnect. One blip or laptop sleep ends the stream permanently,
  despite `since=<cursor>` existing precisely to resume it.

**What to do**

- Emit `role_invocation_started` before the backend call and `role_invocation_progress` on a ~20 s
  timer while it runs, carrying role, task, model and elapsed. Additive rows in `lexicon_data.yaml`.
- Refetch `/view` (debounced) whenever a non-technical event lands. Zero backend change; it is the
  difference between a brief that grows in front of you and a static page with a log underneath.
- Reconnect with backoff using the cursor already tracked in `SSEClient`.
- Replace the event log with a narrator: one present-tense sentence that rewrites in place, with the
  transcript collapsed behind it. `[47] researcher — attempt 1: ok` is a debug view.

*Backend: two additive audit events plus two lexicon rows. Everything else is frontend.*

## 03 — The pipeline is a graph; the UI draws it as a straight line

**Severity: high.**

`MethodStrip` renders six phases and marks them by index comparison. The state machine has four
backward edges, and — verified against `_STAGE_TO_PHASE` in `orchestrator/service/caseview.py:74` —
**every one of them is intra-phase**, so the strip does not move at all while a loop runs.

That is worse than a bar going backwards. Three of the six blocks are cycles, not steps:

| Phase | Cycle | Cap |
|---|---|---|
| Framing | `awaiting_framing_approval → framing` | 2 |
| Challenge | `stop_decision → repair → challenge` | 2 repair cycles |
| Synthesis | `review → synthesis` | 1 |
| Synthesis | `awaiting_final_approval → synthesis` | 1 |

A case can go around the challenge loop twice — twenty minutes and a third of its invocation budget
— and the interface renders the same static block throughout. A second round is pixel-identical to a
stall.

**What to do**

- Replace the strip with a case map that draws the cycles permanently, so a loop is a visible part
  of the plan before it runs rather than a surprise when it does.
- Put a round counter on every cycle. "Challenge — round 2 of 2" is the cheapest fix in this
  document: `CaseState.repair_cycle` already holds it, and it is the only thing that distinguishes
  productive re-work from a hang.
- Announce loops in plain language when they fire: "The challenger found a material objection to the
  cost assumption. Going back to research one question — about 6 more minutes."
- Make loop budgets first-class. `repair_cycle`, `synthesis_retries`, `framing_revisions` and
  `final_revisions` are all in `CaseState` and visible today only as raw meters in the Method room.
  They encode the system's most legible promise: it argues with itself at most twice, then commits.

*Backend: none. Every counter is already in the projection.*

## 04 — One density for two audiences

**Severity: high.**

Some users want to ask and get an answer; others want to be in it. Everyone currently gets the same
thing: seven routes, five rooms, an inspector, and a case page whose first content is a definition
list containing the row `Terminal: no`.

- `frontend/src/pages/CaseDetail.tsx:36` — internal state rendered as a spec sheet.
- `frontend/src/App.tsx:43` — `CaseDetail` and `Brief` both render `brief_sections`, so there are two
  competing "home" screens for a case.
- `frontend/src/screens/rooms/` — five rooms are five full-page navigations; following a claim into
  Sources loses your place in the argument.

**What to do**

Do not build two products. Build one page with an altitude control, because the deep audience is not
a different person — it is the same person at a different moment.

1. Three altitudes, remembered per user rather than per case: **Answer** (recommendation, one honest
   sentence of uncertainty, three reasons, what would change it), **Reasoning** (the brief with
   provenance and citations), **Method** (rooms, inspector, gates, raw artifacts, spend).
2. Turn the rooms into a context panel rather than routes — the inspector already works this way.
3. Ask at commissioning what shape to hand back: a one-page answer or a full advisory brief. It sets
   the default altitude and nothing else.
4. Make every claim expandable in place. Depth on demand beats depth by navigation.

*Backend: none. Information architecture over the existing projection.*

## 05 — The checkpoints are form-walls, and the answer arrives behind instruments

**Severity: high.**

The two signed checkpoints are where the product asks you to take responsibility. Both present
everything at once with no sense of what matters.

- `frontend/src/screens/ScopeCheckpoint/ScopeCheckpoint.tsx` — 539 lines rendering a restatement
  textarea, an editable options list, outline checkboxes, ground-rule confirmations, effort columns
  and a signature block, all expanded simultaneously with equal weight.
- `frontend/src/screens/Delivery/Delivery.tsx:131` — the answer card is immediately followed by four
  uncertainty widgets, *then* the reasons. For the ask-and-answer audience the second thing they see
  is a grid of instruments.
- `frontend/src/copy/terms.ts` (`NEEDS_YOU`) — the consequence-of-doing-nothing copy is genuinely
  good and is rendered as a small grey line instead of leading the screen.

**What to do**

- Scope: lead with the restatement and a binary — "Here's the decision I'll actually answer. Is that
  right?" — with the other sections collapsed under *Adjust scope* and a count of what is inside
  each. One click to sign, or open everything. The audit record is identical either way.
- Delivery: lead with one honest sentence synthesized from the four measures rather than replacing
  them ("Buy the ETF. Roughly a 65% chance this beats the alternatives over 12 months. I'm
  moderately confident, and the evidence is thin on one point"). The four encodings move one click
  below under *How sure is this?*, unchanged.
- Put the consequence line in the subhead of both checkpoints.
- Confirm the send-back. It consumes the only revision available (`MAX_FINAL_REVISIONS = 1`) and the
  UI currently spends it on an unconfirmed click.

*Backend: none.*

## 06 — There is no story for the three hours you are away

**Severity: high.**

The first verified real case took 191 minutes. The UI's honest advice is "You can leave the page."
Nobody who leaves is told to come back: no tab title, no notification, no digest on return — even
though every event carries a line cursor and the stream accepts `since=`.

**What to do**

- Tab title as a progress channel: `(3/6) Investigating · AgentAdvisor`, and `✓ Ready for you` at a
  gate. Works in a background tab all afternoon.
- Notification on the two moments that need a human, plus failure. Ask for permission when the first
  case starts running, when the reason is obvious.
- A "while you were away" card on return: persist the last-seen cursor, reconnect with it, and
  summarize the gap ("11 evidence records, the thesis changed from ETF to staged entry, 2 objections
  raised, 1 gate failed and was repaired"). Client-side, from events already received.
- Live spend in the header. Invocations, tokens and wall clock against caps are all in `EffortView`
  and surfaced only inside the Method room. On a run that can cost 1.5M tokens that belongs up top.

*Backend: none.*

## 07 — Eight CSS variables and forty-five loose hex values

**Severity: medium.**

`frontend/src/styles.css` is 1,364 lines built on eight custom properties, with roughly forty-five
raw hex values written inline across component rules. No type scale, no spacing scale, no elevation,
no dark mode, one fixed 960 px column, and `<p>Loading…</p>` as the loading state on every screen.
This is what reads as "primitive" before anyone notices the deeper issues.

**What to do**

- A token layer first — color, space, type, radius, elevation, motion — with semantic aliases
  (`--surface-raised`, `--state-needs-you`) on top. Every one of those hexes maps to a token. A
  mechanical change that unlocks everything else.
- Dark mode falls out of it once components stop naming colors directly.
- A three-region shell (case rail / content / context panel) instead of one stacked column.
- Skeletons shaped like the content, not the word "Loading".
- Toasts for control actions. Approve, pause, resume and send-back currently either silently swap
  the screen or render a red paragraph.
- Then spend the design budget in exactly one place: a **calibration language**. Bands rather than
  bars, dots you can count, an explicit *Not assessed* stamp — one consistent visual vocabulary used
  at every altitude, from the answer headline down to a single evidence chip. Everything else stays
  quiet so that reads.

*Backend: none.*

## 08 — The library is a table, and the time promise is not true

**Severity: medium, plus one trust bug.**

The case list is three columns of text with no progress, no spend, no search and no grouping. For a
product where a case is a multi-hour engagement, the list *is* the dashboard, and it shows less than
`advisor status` does in a terminal.

**The trust bug.** `EFFORT_PROFILES` in `frontend/src/copy/terms.ts` promises "roughly 10–20 minutes"
for Standard and "30 minutes or more" for Deep. The first verified real case took **191 minutes and
1.58M tokens**. A product whose entire pitch is epistemic honesty cannot open with an estimate off by
an order of magnitude. This should be fixed before any of the visual work — it costs one edit and it
is the first promise the product makes.

**What to do**

- Derive the ranges from recorded history. `memory/` already stores prior cases; show a measured
  p50–p90 per effort profile and say it is measured. With no history yet, "first runs have taken 40
  minutes to 3 hours" — true beats precise.
- Cards, not rows: live phase ring, elapsed vs. estimate, spend against cap, the current narrator
  line, and the needs-you state encoded as form and not only color. Grouped *Waiting on you* /
  *Running* / *Done*.
- Let the server say what needs you. `frontend/src/pages/CaseLibrary.tsx:7` re-derives `needs_you`
  from a stage string, duplicating logic the projection already owns. Add the field to the list
  endpoint and delete the duplicate.
- Command-K across cases, evidence and assumptions once there is more than a handful of cases.

*Backend: one optional field on the list endpoint.*
